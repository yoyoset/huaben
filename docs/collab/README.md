# 协作规则:架构方定方案,执行方照卡实施,文档是唯一的沟通渠道

2026-10-03 用户定:架构方(Claude)成本高,只管方向、架构、方案和验收;具体实施交给便宜的执行模型(flash 等)。
两边不直接对话——直接对话的成本等于架构方自己做。所以一切靠这个目录里的文档。

## 文件与归属

| 文件 | 谁写 | 内容 |
|---|---|---|
| `BOARD.md` | 两边(各改各的列,见下) | 任务队列与状态,唯一的"下一步做什么" |
| `tasks/Txxx-*.md` | **只有架构方** | 任务卡:为什么做、已定的方案、改哪些文件、验收标准、不做什么 |
| `reports/Txxx.md` | **只有执行方** | 执行报告:做了什么、命令的真实输出、偏差、问题 |
| `README.md`(本文件) | 只有架构方 | 规则 |

执行方**不许改**:`tasks/`、本文件、`CLAUDE.md`、`AGENTS.md`、`docs/architecture.md`、`BUILD_LOG.md`、`docs/build-log/`。
(路线与构建日志由架构方在验收通过后统一记录,免得两边写出两套说法。)

## 状态流转

```
待做 ──执行方开工──> 进行中 ──执行方交付──> 待审 ──架构方──> 通过
                        │                          └──────> 打回(卡片末尾写打回意见,状态改回「待做」)
                        └──执行方做不下去──> 卡住(报告里写清问题,然后去做下一张不依赖它的卡)
```

执行方只能把状态改成:进行中 / 待审 / 卡住。「通过」「打回」只有架构方能写。

## 执行方的工作流程(每张卡)

1. 读 `BOARD.md`,取**最上面一张**「待做」且"依赖"已通过(或为"无")的卡。把状态改成「进行中」。
2. 完整读卡。卡里"已定的方案"是决定,不是建议——**不要改方案**。觉得方案有错或做不到:停,状态改「卡住」,
   在报告"问题"一节写清楚哪里不对、你看到了什么,然后做下一张卡。
3. 只改卡里"改哪些文件"列出的文件。需要动别的文件才能完成:最小限度地动,并在报告"偏差"一节逐个列出为什么。
4. 写代码 + 写卡里要求的测试。
5. 跑验收命令,把**真实输出**贴进报告(至少最后 15 行)。没跑过的不许写"通过";跑了失败的,贴失败输出。
6. 复制 `reports/_TEMPLATE.md` 为 `reports/Txxx.md` 并填写。
7. 提交:**一张卡一次提交**,代码 + 报告 + 看板状态一起。提交信息第一行 `Txxx: 做了什么`,正文写真实依据(数字、命令结果)。
8. 把看板状态改成「待审」(包含在同一次提交里)。接着做下一张卡。

## 硬规则(以前踩过的坑,每一条都有来历)

1. **不要自己加任务。** 想到值得做的事,写在报告"建议"一节,由架构方决定要不要出卡。
   来历:上一轮执行方自己往路线里加了 65~70 六项并全部"完成",其中多数只是往提示词里加了一句话。
2. **不要靠"往提示词里加一句要求"解决问题**,除非卡里给出了要加的原文。提示词已经很长,每加一句都在稀释别的要求。
   卡里给了原文的,**一字不改地照抄**(包括标点)。
3. **"实测"必须是真的跑出来的结果。** "这句话出现在提示词里了"不是实测,只说明代码被执行了。
   没条件实测的(要 GPU、要密钥、要生产数据),在报告里明说"未实测,原因是……",不要用别的东西顶替。
4. **不要部署,不要碰生产**(10.1.1.13)。部署和生产副本实测由架构方在验收时做。
5. **不要碰密钥**,不要往任何地方填 key。
6. **不要删除或覆盖用户已有的内容**(旧引擎、旧配置、旧文档并行保留)。卡里明确写"删除 xxx"的除外。
7. **单个 .py ≤ 200 行**(`tests/test_structure.py` 强制)。超了按职责拆文件,**不许调高上限**,不许为了凑行数把多行挤成一行。
8. **改代码用编辑工具**,不要用 shell 的 heredoc/echo 写含 `\n`、`\u`、全角标点的源码(会被吞转义,踩过)。
   仓库里 CRLF/LF 混用,保持每个文件原来的换行风格。
9. **测试不碰网络、不碰 GPU**:用 `FakeLLM` / `FakeEngine` / 剧本 LLM。
10. 同一个问题修了 3 次还没好:停,状态改「卡住」,报告里写清楚三次各试了什么。不要无限试下去,也不要为了让测试变绿去改测试的断言。

## 架构方的工作流程(给 Claude 自己看)

用户说"审一下"或开新对话时:

1. 读 `BOARD.md`,对每张「待审」:读报告 → `git show` 看这次提交的真实改动 → **自己重跑**验收命令(不信报告里贴的输出)。
2. 对照卡里的验收标准逐条核对;需要生产副本实测/部署的,此时由架构方做。
3. 通过:看板标「通过」,把结果记进 `BUILD_LOG.md` 与 `docs/build-log/`。
   打回:在卡片末尾"审核记录"写**具体哪一条不符、期望是什么**,状态改回「待做」。
4. 处理「卡住」的卡:回答报告里的问题(写进卡片的"审核记录"),必要时改方案。
5. 根据报告里的"建议"和用户的新要求出新卡。卡要写到执行方**不需要做判断**的程度:
   方案定死、文件点名、提示词给原文、验收给命令。需要判断的事不下放。
