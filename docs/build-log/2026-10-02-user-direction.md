## 3. 配音以电脑为主(ce89d61 + 电脑端程序)

- 先查清事实再设计:爱读(aidulc)的"高质量朗读"是 **Kokoro-82M**,由爱读桌面程序拉起的命令行进程(stdin/stdout),
  不是网络服务;而且**只配了英文**(语言表里英文→`a`,另一门→`j`),本机只下载了英文音色 `af_heart`,
  中文前端依赖(jieba/pypinyin/cn2an)也没装。用户回复:Kokoro 只是举例,中文要用对应的中文模型。
- 服务器(`HUABEN_TTS_MODE=pc`,默认)不自己配音,出任务队列;电脑上的程序**拉取**任务、交 MP3(电脑不用开端口)。
  任务顺序:每本书按读者接下来要听的,多本书轮流取(`voice_queue.interleave`)。
- 两份音频并存:basic=edge、hq=电脑;播放优先 hq,文件丢了退到另一份;音频地址带版本(`?v=1_0004.hq.mp3`),
  升级后浏览器不会继续播缓存里的旧版。
- 电脑离线(10 分钟没来取任务):书页与书架提示"有 N 章在等电脑配音,请打开电脑上的配音程序",
  书页可点"先用 edge-tts 配"(只配一份音频都没有的章;电脑开机后照样升级)。电脑在线时显示"正在配音"。
- 电脑端程序 `pc_worker/huaben_voice`:一次取一章 → 合成 → 交回;没任务歇 30 秒;出错指数退避、不退出。
  引擎接口 `synthesize(text) -> MP3 bytes`,目前只有 `fake`。
- MP3 编码:实测爱读环境里的 soundfile 0.14 / libsndfile 1.2.2 能直接写 MP3(24kHz 写出的是 MPEG-2 帧 `FF F3`),
  服务器的 `is_mp3` 按帧同步字判断,接受。

验证:服务器侧 9 个测试 + 电脑端 5 个测试(对着真的 FastAPI 接口端到端跑:按听的顺序取、配完队列清空、令牌、
出错退避不退出);浏览器用替身 TTS 走通"提示 → 先用 edge → 电脑上线显示正在配 → 交 MP3 → 播电脑版"。

## 7. "核对"打回的真实原因;电脑端双击启动器

**用户看到"第 13 章:连续几稿都没通过核对"。** 查生产库 pipeline_runs:第 13 章两轮共 6 稿**全部**被"照抄前文"打回
(12 字片段与前 3 章重合 35% / 24% / 21% / 97% / 11% / 76%),第三轮才写过去;第 14 章第 1 稿也是 12%。
已定稿章之间的重合从第 4 章 0.4% 一路涨到第 14 章 3.6%(开头复述上一章结尾:"掀开枕头。底下压着一张纸条")。
最初以为是检查误判,实测是模型真的在照搬——写作提示里摆着最近 3 章全文(约 9000 字)。
修复:写正文只给最近几章的**章摘要** + 上一章**结尾 1200 字**(章纲提示仍带原文)。提示也因此短了约 6000 字。
效果要在生产上看后续章节的打回率,未验证前不改"照抄前文"的 8% 阈值。

**电脑端配音改成双击启动(用户:"别用命令,要双击的 exe,带 logo,让我知道可以关闭,别黑箱")。**
`pc_worker/HuabenVoice.exe`(桌面快捷方式「话本配音」),源码 `pc_worker/launcher/`,Windows 自带 csc 编译,零新依赖。
窗口一行状态 + 全量日志(另存 `pc_worker/logs/`),托盘图标;关窗 = 停止,最小化 = 后台继续;单实例;
子进程放进"关闭即结束"作业对象——实测强杀启动器后 uv 转发器与真 python 两个进程都退出(剩 0)。
踩坑:`.cmd` 是 LF 换行时 cmd.exe 把行拆碎乱执行;管道下 Python 默认 GBK + 整块缓冲(设 PYTHONIOENCODING / PYTHONUNBUFFERED);
写死像素高度的标签在高 DPI 下截字;jieba 加载时刷一屏 SyntaxWarning,看着像出错(PYTHONWARNINGS 屏蔽)。

暂不做:开机自启(等用户点头);重复打开时把已有窗口提到前台(现在是弹框说"已经在运行,看托盘")。
