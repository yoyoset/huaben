## 15. 深链到还没写好的章

## 第二轮审查:数据从哪来到哪去(路线 1~16 清空后)

方法:沿五条数据路径逐段读代码,问"这一段的输入从哪来、输出到哪去、失败/并发/重启时会怎样":
1. 开书:对话 → 圣经 → 第 1 卷 → serializing;2. 补货:进度 → 缓冲 → 章 → 账本 → 配音 → 文件;
3. 收听:音频 → 播放器 → 进度上报;4. 花费:上游 usage → pipeline_runs → 安全阀/统计;5. 后台:worker → 每本书 → 界面状态。

发现(已追加为路线 17~23,按严重度排序):
- **配音一轮做完所有缺口**(17):`chapters_needing_audio` 按章序返回全部,`fill_audio` 无上限、在书锁内跑完;
  worker 是单线程逐书巡检,所以一本书大规模重配会拖住所有书。第 11 项("丢失文件要重配")让这个场景变得现实。
- **文字写满缓冲才配音**(18):`_fill` 先循环写文字,循环结束才 `fill_audio`。
- **章内播放位置不持久**(19):`audio.currentTime` 不落到任何地方。
- **费用口径依赖上游**(20):`cost_usd = usage.cost or 0`,`openrouter_base_url` 可配成别的兼容接口。
- **开书无并发保护**(21):前端在请求期间禁用按钮,但离开再回来会重新启用;后端无锁,卷表 UNIQUE(book_id, idx) 是最后防线(500)。
- **自动播放被拒**(22):`play()` 里 `await audio.play()` 抛 NotAllowedError 时,`ended`/`waitForNext` 的调用方没有 catch。
- **LLM 不可用时书页无状态**(23):`Worker.tick` 在 `ensure_llm` 失败时直接返回,不写任何书的可见状态。

确认没问题的(记下来,下一轮不必重查):补货并发由书锁保证;进度上报"只增不减"与补货触发一致;半成品章在下次生成前清掉,
不占号、不入账;封卷失败不改任何东西;开书"缺什么补什么"可重试。
需要用户决策、不进路线:书架没有"归档/删除书"(用户偏好是不随手删内容;是否要"从书架隐藏但保留数据"由用户定)——已记 Magpie 点子池。

## 17. 配音的先后与每轮上限

实测(改动前,同一场景脚本):30 章都缺音频、读者停在第 25 章,一次 `top_up` **配了 30 章,从第 1 章开始**——
一轮里一直占着这本书的锁;worker 是单线程逐书巡检,这期间所有书都不补文字。

做了(`huaben/tts/service.py`):
- `listening_order(chapters, pos)`(纯函数):先配从当前章往后的(读者接下来要听的),再往回补已经听过的,越近越先。
- `audio_round_limit(settings)` = 缓冲章数 + 1:正常连载时一轮新增的章不超过缓冲章数,加上正在听的这章,所以平时碰不到上限;
  只有恢复备份后大批重配才分轮进行,每轮放锁。没配完不算错误(`audio_error` 为空),下一轮从剩下的接着配。
- `top_up` 以书的 `last_opened` 为起点、按上限调用 `fill_audio`。
验证:新测试复现上述场景 → 第一轮只配 25~28,第二轮 29、30、24、23;排序纯函数的边界(没读过从头、空列表);全量 241 个通过。
暂不处理:大批重配的总耗时不变(只是分摊到多轮,每轮之间隔一个巡检间隔);不显示"还有 N 章在配音"的进度。

## 18. 写好一章就配一章

实测(改动前,新测试在旧代码上跑):新书补货写 3 章,三次配音都发生在第 10 次模型调用之后(`[10, 10, 10]`)——
第一章写好后,读者要再等两章的生成(每章一两分钟)才能听。
做了:`scheduler._fill` 每定稿一章随即配音(limit=1,仍按 `listening_order` 取最近的缺口),并从本轮配音上限里扣掉;
文字补完后再用剩余额度补其它缺口。配音失败只记下、不打断文字,本轮之后不再尝试(留给配音退避),避免每章都白等一遍超时重试。
验证:新测试 → 配音发生在第 4、7、10 次调用之后;中途配音失败时文字照常写满 3 章且只尝试合成 1 次;全量 243 个通过。
暂不处理:文字与配音仍是同一线程串行(配音期间不写下一章);真要并行得等真实 edge-tts 耗时数据再决定。

## 19. 听书记住章内位置

做了:
- `web/js/listen_pos.js`:本机记每本书最近在听的 `{章, 秒}`(读写包 try/catch,存储不可用时只是不记忆)。
- 纯函数 `logic.resumeAt(saved, idx, duration)`:同一章接着播并回退 3 秒接上文;记的是别的章、只听了不到 5 秒、
  离结尾不到 10 秒(多半是想重听)→ 从头。
- 播放器:元数据到了才知道时长,在 `loadedmetadata` 里决定跳不跳,并提示"接着上次的位置(36 秒)";
  播放中每前进 5 秒、暂停、`pagehide`(页面被关/被杀前的最后机会)各记一次;一章播完清掉。
  自然播完时浏览器会先发 `pause` 再发 `ended`,所以 `pause` 里用 `audio.ended` 排除,免得刚清掉又写回去。
决策:只存本机。要解决的是"同一台手机重开后接着听";跨设备续听要每几秒写一次服务器,先不做。
验证:node 测试 7 个分支;浏览器(约 52 秒的静音 MP3):播放中跳到 30 秒 → 本机记下 30;整页重载(模拟被杀)时 `pagehide` 记下 39;
再点"听这一章" → 从 36 秒开始并显示提示;跳到结尾 → 记录被清掉,自动接第 2 章从 0 秒播。
暂不处理:跨设备续听;iOS 真机上 `pagehide` 在被系统杀掉时是否一定触发——有每 5 秒一次的记录兜底,最多丢 5 秒。

## 21. 同一本书不能并发开书

最初以为(审查时读代码推断):第二个开书请求会在规划第 1 卷时撞卷表唯一约束,得到 500。
实测(旧代码,第一个请求卡在整理圣经的模型调用里时发第二个):**两个请求都成功了**——第二个完整跑完(圣经 + 第 1 卷规划),
第一个随后继续,**再整理一遍圣经并覆盖掉第二个的结果**,卷已存在所以不再规划。也就是:重复花钱,而且开书后书名/人物可能被悄悄换掉
(真实模型两次输出不同)。500 只在两者恰好同时走到规划卷时出现。
做了:
- `opening/service.py`:按书的进程内锁,对话(`opening_turn`)与定稿(`finalize_book`)共用;拿不到锁抛 `OpeningBusy`。
  共用的理由:定稿期间补发的话不会被漏进圣经(圣经按定稿开始时的对话整理)。
- 路由把 `OpeningBusy` 映射为 409;`api.js` 的错误带上 `status`。
- 开书页:收到 409 不当失败,按钮显示"正在开书(之前那次还在进行)…",轮询书的状态,开好了直接去阅读。
验证:3 个新测试(进行中时再定稿/再对话都被拒、最终只调模型 2 次只有 1 卷;API 回 409;失败后锁会释放);全量 249 个通过;
浏览器里拦截 fetch 模拟 409 → 不显示错误、按钮进入等待、约 5 秒后跳到阅读页。
暂不处理:第一次开书失败时,等待中的页面要到轮询放弃才恢复按钮(那次失败的错误会显示在发起它的页面上);多进程部署需要库级租约(与补货锁同一前提)。

## 22. 自动续播被浏览器拦下时给出提示

做了:

自动换到第 2 章、暂停状态、提示"点 ▶ 继续播放第2章"、没有上报第 2 章、没有未处理的 Promise 拒绝;恢复后点 ▶ → 上报第 2 章一次,

## 23. 没有可用模型时,书页显示原因

## 24. 前端壳文件每次用前向服务器确认(Cache-Control: no-cache)

实测(改动前):静态文件响应只有 `ETag` 与 `Last-Modified`,没有 `Cache-Control`。浏览器于是按启发式新鲜度直接用缓存;
第 23 项验证时服务器已返回新代码,整页重载后仍执行旧模块。service worker 里"网络优先"的 `fetch()` 走同一层 HTTP 缓存,
所以 sw.js 注释里"改了前端代码刷新就能生效"并不成立——**最初以为网络优先就够了,实测不够**。
做了:`huaben/api/static.py` 的 `RevalidatingStaticFiles` 给壳文件加 `Cache-Control: no-cache`(用前先问,没变回 304、不传正文);
sw.js 注释改正。没选"文件名带哈希 + 长缓存",因为前端刻意不做构建步骤;家用网络下每个模块一次 304 往返可以忽略。
验证:7 个新测试(各类壳文件带 no-cache 与 ETag;带 If-None-Match 回 304 且无正文;/api 不被静态挂载盖住);全量 258 个通过。
浏览器:加载后在磁盘上临时改书架标题 → 整页重载,网络记录里其余模块全是 304、只有 shelf.js 是 200,页面显示新标题(临时改动已还原)。
暂不处理:音频(`/api/.../audio`)仍按启发式缓存——同一章的音频内容不变,缓存反而省流量;丢失重配后文件内容相同。

## 第五轮审查 + 28. 被丢弃但已计费的调用也要记账

审查范围:模型客户端(重试、超时、CLAUDE.md 要求的"关思考、两项惩罚为 0")与调用记账。
确认没问题的:payload 固定 `frequency_penalty=0`、`presence_penalty=0`、`reasoning.effort="none"`;4xx 不重试、5xx/429/网络错误重试;
被截断(finish_reason=length 但有正文)照常返回并带 `truncated`,由流水线打回重写且照实计费。
发现(→ 28,中·实测):"200 + 空正文"(思考吃光 max_tokens 的典型形态)**照样计费**,但客户端丢弃这次结果去重试,费用不进任何记录;
最终失败时 `call_step` 记的也是 0。脚本实测(MockTransport,连续 3 次空回复,每次 $0.012):上游计费 $0.036,记录 $0.000。
花费上限要防的"模型异常、每次都白烧"恰好就是这个形态——它对此完全失明。
做了:
- `LLMError` 增加 `tokens_in/tokens_out/cost_usd`(默认 0);`parse_response` 先读 usage 再抛 `LLMEmptyError`,带上本次计费。
- 客户端累计被丢弃尝试的计费:最终成功则并入返回结果,最终失败则写进抛出的错误。
- `call_step` 失败时把错误上的 token/费用记入 pipeline_runs。
验证:3 个新测试(全空 → 记 $0.036、ok=0、24000 token;空一次后成功 → 结果含 $0.016;普通成功不变);旧代码上前两个失败;全量 269 个通过。
暂不处理:HTTP 5xx/429 的失败按惯例不计费,未记;若上游某天对失败请求计费,需按其账单核对。

## 第六轮审查 + 29. 真实配音加总超时

审查范围:模型输出的 JSON 提取、真实配音适配层(EdgeTTS)、朗读前文本处理。
确认没问题的:JSON 提取容忍围栏与前后说明文字,取不出就显式失败交给重试;朗读切块不丢字、不重复(已有测试)。
发现(→ 29,中·实测):`EdgeTTS.synthesize` 没有自己的超时,`requirements.txt` 只写 `edge-tts>=6`,库的内置超时因版本而异、
不能依赖。实测(替身 edge_tts,stream 挂住):旧适配层被外部 5 秒强杀时仍在阻塞。后台是单线程逐书巡检——一次挂住就是所有书停更,
而 /api/health 的 worker 仍显示 running。
做了:`asyncio.wait_for` 包住整段合成,超时变 `TTSError`("配音请求超过 N 秒没有完成"),走既有的配音失败 → 退避 → 界面提示路径;
`HUABEN_TTS_TIMEOUT_S`(默认 120 秒,单块 ≤1500 字正常十几秒)。
验证:3 个新测试(替身 edge_tts:拼接音频块;挂住 0.2 秒超时内返回 TTSError;空音频报错);全量 272 个通过。
暂不处理:依赖版本只写了下限(`>=`),Docker 构建可能拉到不兼容的新大版本——锁定版本要在首次真实构建、实测通过后按实际版本写死,
已记 Magpie(需要在 13 上构建,不在本地做)。
