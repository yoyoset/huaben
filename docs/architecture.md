# 架构与关键决策

状态:2026-10-01 头脑风暴定稿;2026-10-02 起 v0 在本地实现(进度与踩坑见 BUILD_LOG.md),本文决策无变更。每条决策都写了"为什么",推翻时请同时改掉理由。

## 1. 产品形态

| 决策 | 为什么 |
|---|---|
| **PWA 网页应用**,不做 APK | 家里有 iPhone 用户,APK 直接排除她;PWA 可"添加到主屏幕",一套代码双平台。真需要上架/更强后台能力时再套安卓壳。 |
| **锁屏听书靠预生成 MP3 + `<audio>` + Media Session API** | 酒馆用浏览器 speechSynthesis 实时念,锁屏就停;播放现成音频文件则 iOS/Android 都能后台播并显示锁屏控件。(待真机验证,见"风险") |
| 远程访问用 **Tailscale** | 用户已有 Tailscale,不做账号系统、不做公网暴露。 |
| **每人一个书架(profile = 人),不要密码** | 2026-10-02 用户要求:家里几个人("我老婆是她的 profile,我是我的")各自开书、各自进度。打开先选"谁在看",选择记在本机。没有密码:Tailscale 已挡住外人,家里人之间不需要防。书各归各,不做共享与删除人。 |

## 2. 部署与算力:生成与收听解耦

| 角色 | 跑在哪 | 职责 |
|---|---|---|
| 主服务 | **10.1.1.13**(常开,Docker Compose,`/opt/huaben`) | PWA、API、数据库、故事引擎(调 LLM,无需 GPU)、配音任务队列;edge-tts 只作手动备用 |
| 配音工人 | 用户的 PC(RTX 3060,开机才在) | **主动拉取**主服务的配音任务,用本地中文 TTS 模型合成 MP3 交回(`/api/voice/*`) |

- **预生成缓冲**:始终比读者进度多备好 N 章(默认 3)的正文。正文生成**永远不依赖 PC**。
- **配音以 PC 为主(2026-10-02 用户改定)**:最初的设计是"edge 保底 + PC 升级,PC 只是增强"。用户看过之后改为:
  配音以 PC 上的本地中文模型为主,"不要死磕 edge-tts";PC 没开时**提醒开机**,并让读者决定要不要"先用 edge-tts 配"
  (`HUABEN_TTS_MODE=pc`,默认)。理由:用户在意音质胜过"随时有声音",且 PC 由自己控制,等得起。
  两份音频并存(basic=edge、hq=PC),播放优先 hq;先用 edge 配过的章,PC 开机后照样升级。`HUABEN_TTS_MODE=edge` 可回到旧行为。
  任务顺序:每本书按"读者接下来要听的"排,多本书之间轮流取(家里几个人各自在听)。
- 工人用"拉"模式(轮询主服务队列),PC 不需要暴露端口;经 LAN 或 Tailscale 访问主服务。

推荐技术栈(新对话开工时可再议):后端 **Python + FastAPI + SQLite**,沿用 13 上 vpsmon / opencode-usage 的惯例
(Docker Compose、`config/` 只读挂载、`.env` 存密钥不进代码);保底 TTS 直接用 Python `edge-tts` 库输出 MP3
(不要再走酒馆插件那条路,见踩坑记录)。备份沿用酒馆方案:每日打包到 `/mnt/4t/backups/huaben`。

## 3. 故事引擎:编辑与作者分离

核心思想:**遗忘的解法是结构化状态,不是更大的记忆。**模型不需要记住全部,只需要每章读一份由程序维护的"工作台"。

### 3.1 数据模型(概念层)

- **读者 Profile**:一个人(名字唯一);每本书属于一个读者
- **书 Book**:标题、类型、开书对话记录、所属读者
- **故事圣经 Bible**:世界观与规则、人物卡、**风格指纹**(从样章提取)+ 样章片段
- **卷 Volume**:目标、节拍、本卷要埋/要收的伏笔、状态(规划中/连载中/已封卷)、封卷摘要
- **章 Chapter**:章纲(内部工单,读者不可见)、正文、章摘要、音频版本(保底/高质量)
- **账本 Ledger**(跨卷常驻):
  - 人物现状(生死、位置、能力、关系)与**谁知道什么**
  - 伏笔清单:埋于第几章、计划何时以何种方式回收、状态(已埋/推进中/已收)
  - 伏笔大小(2026-10-02 用户要求,迁移 9):短线 3~5 章内收 / 中线本卷内收 / 长线跨卷只给线索不揭底。
    入账时由编辑标注;写章纲时按大小算出"该收了/拖欠",到期的必须回收一条,未收的短中线过多时不再开新坑
    (规则见 `huaben/foreshadow_scale.py`)。起因:生产 14 章埋 23 条只收 1 条,约定与身世之谜记得一模一样。
  - 已确立的世界事实:本卷内逐条记录(去重);**封卷时并入圣经里的"世界设定定本"**(canon)

### 3.2 每章流水线

1. **编辑·卷规划**(仅在需要新卷时):根据圣经 + 账本 + 往卷摘要,规划下一卷——目标、节拍、伏笔的埋与收。读者看不到。
2. **编辑·章纲**:根据卷规划 + 账本 + 近期摘要,写本章工单(发生什么、触及哪些伏笔、结尾钩子)。
3. **作者·正文**:根据章纲 + 圣经(含风格指纹与样章片段)+ 分层记忆 + 最近几章原文写正文。
4. **编辑·入账**:抽取章摘要;更新账本;**核对矛盾**——与账本冲突且不是章纲里计划好的反转 → 打回重写。
5. **语音**:入队生成保底 MP3(v1 再加导演脚本 + 高质量语音)。

> "故意反转"和"写着写着忘了"对读者是两回事:前者是爽点(他居然没死!),后者是硬伤。
> 账本的意义不是禁止矛盾,而是让每次打破设定都是**有意为之**——前提是系统清楚地记得那个事实。

### 3.3 分层记忆(按故事结构压缩)

| 层 | 内容 | 写每章时 |
|---|---|---|
| 全书梗概 | 几百字:这是什么故事、走到哪了 | 全带 |
| 往卷摘要 | 每卷一段 | 全带 |
| 本卷章摘要 | 每章两三句 | 全带 |
| 最近原文 | 保证文风和情绪衔接 | 3~5 章 |
| 账本·人物 | 现状/知情 | 核心人物全带;其余按检索范围挑(写作 = 章纲,核对 = 章纲 + 正文)。谁是核心由开书圣经定,入账不能改 |
| 账本·伏笔 | 未回收的 | 全带 |
| 世界设定定本 | 往卷事实合并去重后的要点 | 全带 |
| 本卷新事实 | 本卷逐条确立的事实 | 全带 |

**封卷**:一卷结束时压成卷摘要、本卷事实并入定本、原文归档,于是第 500 章的 prompt 体量和第 50 章差不多。

> 事实**不按条数截断**(2026-10-02 修正):最初的做法是"只带最近 40 条",会最先丢掉最早、最根本的设定,
> 而且写作和核对同时看不到它——相关矛盾从此查不出。改为与章节同样"按故事结构压缩"。
>
> 代价是定本的长度只靠模型合并时去重来控制。所以对它**只观测、不截断**:每次封卷在运行记录里留"定本 旧→新 字",
> 超过 4000 字(`huaben/canon_size.py`,比一章正文长得多)记日志告警、统计页标红,由人判断是设定本来就多还是合并没去重。

### 3.4 结构:卷,而不是完结

故事没有终点,只有"告一段落"——网文的**卷**(外门篇、下山篇……)。读者愿意看就一直往下。卷是规划单位,也是记忆压缩边界。

## 4. 用户介入

- **默认一键连载。**用户的意图在开书时一次性输入;想要不同的东西 → 开一本新书(所以开书要快,~5 分钟)。
- **开书是引导式对话**,不是表单:类型、参考作品与**样章**(风格从这来)、雷点、爽点密度、篇幅。
- 中途"引导剧情"做成**默认关闭的设置项**。
- **"引导"与"品控"分开**:v1 加每章末尾的「不好看」+ 理由(太拖/太水/崩人设/不吓人/不好笑),调整写法但不改走向。
  依据:酒馆期间唯一的真实反馈"剧情太慢"就是品控问题,不是引导问题。

## 5. 听书(人味)

- v0:Edge 晓晓 MP3、Media Session 锁屏控制、自动下一章、睡眠定时。
- v1:**导演环节**——LLM 把章节改写成广播剧脚本(每句:说话人、情绪、停顿),再按角色分配声音合成;
  PC GPU 工人跑表现力更强的本地中文 TTS(候选待实测选型,不在这里预设结论)。
- 判断:人味的主要来源是**旁白/角色分离 + 节奏与情绪**,其次才是音色好不好听。

## 5.5 剧本制:Claude 定故事,flash 只写正文(2026-10-03 用户改定)

**决定**:故事的全部"决定"由 Claude(Claude Code 会话里的架构方)事先写成**剧本**,导入系统;
服务器上的写作模型(flash)只做两件事——照章纲写正文、写完记账。

**为什么**:此前开书、卷规划、章纲、正文、入账全是同一个便宜模型现场生成。实测的毛病(四章没进山门、章章半夜、
13 章埋 29 条没有答案的伏笔、相邻章重演)大多出在"决定发生什么"这一步,而不是文笔。往提示词里加要求治不了:
便宜模型做不了需要通盘考虑的决定。用户的原话:"规划和章纲就你来写,别的也没有你强";话本是家里私用。

**没有选"服务器调用强模型 API"**:要另备密钥、按量付费,且用户明确说不用找别的模型。代价是剧本写完一卷就得回来找 Claude 写下一卷
(约 30 章一次)——可以接受:正文生成在一卷之内仍然不依赖任何人在线。

| 层 | 谁写 | 多久一次 | 放在哪 |
|---|---|---|---|
| 全书设计:真相层(只有作者知道的答案)、人物内核、全书骨架、文风 | Claude | 每本书一次 | `stories/<书名>/design.md`(给人看)+ `book.json`(导入) |
| 卷剧本:卷规划 + **每一章的章纲** | Claude | 一卷 80~120 章,章纲分批写,每批约 30 章 | `stories/<书名>/vol-NN-a.json`、`-b.json`…(导入) |
| 正文、入账、封卷摘要 | flash(服务器自动) | 每章 | 数据库 |

- 剧本书(`books.scripted=1`)写章时不再让模型出章纲,直接取导入的章纲;这一批章纲写完、下一批还没导入时**停更并在书页明说
  "等下一批剧本"**,不许让 flash 自己接着规划。
- **卷的长度与剧本的批次是两回事**(2026-10-03 用户:"30 章是不是少了点,常规小说好几百章才到下一个故事"):
  一卷 = 一段完整的大故事,80~120 章(约 25~35 万字),分三四幕;章纲每批只写约 30 章,因为 flash 实际写出来的会和章纲有出入,
  要读了前一批的实际结果再写下一批。代价:本卷章摘要全带进提示词,100 章约一万字,仍在观测线(24000 字)以内;超了再按幕压缩。
- 写下一卷剧本前,Claude 先读上一卷**实际写出来的**章摘要与账本(flash 不会分毫不差地照章纲写),按实际情况接着设计。
- 伏笔只来自剧本:每条都有真相(见 T007),用"伏笔代号"在章纲之间引用(数据库编号要等写到那一章才产生)。
- 旧流程(开书对话 → 模型定稿圣经 → 模型规划 → 模型章纲)**并行保留**,不删;非剧本书照旧走它。

## 6. 风险(按严重度)

1. **风格模仿**(最大风险):形容词("搞笑、腹黑、热血")只能得到通用 AI 腔;能否靠样章 + 风格指纹写出"那本书的味道"需要最先验证。
2. 编辑·入账的抽取与矛盾核对是否可靠(漏记 = 回到遗忘问题;误报 = 无谓重写)。
3. 每章多次 LLM 调用的成本与时延(需实测;预生成缓冲可以吸收时延)。
4. iOS PWA 锁屏后台播放、自动下一章需**真机验证**。
